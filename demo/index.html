IPC 流式转发：现状与优化建议

当前实现位于 main/ipc/llm.ts，采用 ipcMain.handle 接收请求后，在主进程内消费 LLM 流并逐块通过 webContents.send 推送到渲染进程。

  1. 现状：每个 chunk 一次 IPC 消息，高频小消息在 for await 循环中没有背压控制。
  2. 问题：渲染进程被销毁后继续 send 会抛异常；停止信号依赖渲染进程主动发 llm:abort，主进程未做兜底。
  3. 建议：抽一个 StreamBridge 统一管理流生命周期，集中处理销毁、停止与错误三类收尾。
// main/ipc/llm.ts —— 现状（第 42 行起）
ipcMain.handle('llm:chat', async (event, payload) => {
  const stream = provider.stream(payload);
  for await (const chunk of stream) {
    event.sender.send('llm:chunk', chunk); // 无 isDestroyed 判断
  }
});

改造后每轮会话的 IPC 消息数可以从 N+2 条降为 2 条控制消息 + 数据块批量推送，异常路径也能统一收口。

3.2 IPC 通信的三种模式

schedule约 6 分钟 edit_note3 条批注 auto_awesome由第 3 章原文蒸馏

Electron 的进程间通信表面上只有 ipcMain 与 ipcRenderer 两个模块，但实际使用中会分化出三种截然不同的模式：一次性请求、事件订阅与流式传输。 理解它们的差异，是设计稳定桌面应用通信层的前提。

第一种模式是 Promise 风格的双向调用： ipcMain.handle 与 ipcRenderer.invoke 构成一对请求-响应原语， 适合导入文件、读取配置这类「问一次答一次」的场景。它的好处是错误可以沿 Promise 链自然传播，调用方用 try/catch 就能收口。

事件订阅模式

第二种模式基于 send 与 on 的事件订阅，适合主进程主动向渲染进程推送状态，例如任务进度、托盘通知。 与 invoke 不同，事件订阅没有内建的完成语义，需要自行约定「结束事件」。

经验法则：能用一个 Promise 表达完成的，就不要拆成多个事件； 事件流只留给「持续时间不确定、中途可能取消」的场景。

第三种流式传输则是前两种的混合：以 invoke 建立会话，再以事件通道持续推送数据块。 LLM 流式输出是最典型的例子，本章后续小节会给出完整的背压与取消实现。
